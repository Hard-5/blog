很多人建议「大学一定要写博客」，但理由往往说不清楚。我的理由有三条，都很具体：

1. **写不出来 = 没真的懂。** 看视频、抄代码时大脑会产生「我会了」的错觉，一旦要求用中文把原理讲清楚，漏洞立刻暴露。
2. **这是可以带走的复利资产。** 成绩单只能证明你上过课，笔记和项目能证明你做过什么。两年后简历上的「熟悉 C 语言」远不如一篇讲清楚指针的文章有说服力。
3. **找一个能坚持下去的节奏。** 每周一篇，写什么不重要，重要的是「每周都要有一点新东西值得写」这个倒逼机制。

## 这个博客长什么样

它是一套**零依赖的静态博客**：没有 npm 依赖，没有构建框架，没有数据库，没有服务器。整个网站就是几个 HTML / CSS / JS 文件加一堆 Markdown。

这样选的代价和收益都很清楚：

| 维度 | 这套方案 | 主流框架（Next.js / Hexo 等） |
| --- | --- | --- |
| 上手成本 | 双击 `index.html` 就能看 | 需要装依赖、跑构建 |
| 依赖 | 无 | 几百个 npm 包 |
| 可控性 | 每一行代码都是自己写的，能读懂 | 出问题要翻框架文档 |
| 功能 | 够用（列表、标签、搜索、目录、深浅色） | 插件生态丰富 |

对一个刚入门的人来说，**能读懂全部代码**比功能多更重要——它本身就是一份可以拆开研究的前端教材。

## 日常写作流程

只有三步：

```bash
# 1. 新建一篇文章（自动生成模板 + 重建数据）
npm run new "指针与内存入门" pointers-and-memory

# 2. 用任何编辑器打开 posts/pointers-and-memory.md 写正文

# 3. 重新生成网站数据，然后刷新浏览器
npm run build
```

如果你不想记命令，直接手动在 `posts/` 目录下新建一个 `.md` 文件，然后再跑一次 `npm run build` 也一样。

想本地预览（地址更像正式站点，手机也能连）：

```bash
npm run serve
# 打开 http://localhost:5173
```

## 文章文件的结构

每篇文章开头有一段 frontmatter，用三个短横线包起来：

```markdown
---
title: 指针与内存入门
date: 2026-09-20
tags: [C语言, 基础]
summary: 一句话摘要，会显示在首页列表里。
draft: false
---

正文从这里开始……
```

- `draft: true` 的文章不会出现在网站上，适合写一半先放着
- `tags` 支持 `[a, b]` 或 `a, b` 两种写法
- 不写 `date` 就按文件名或当天日期算

## 目录结构

```text
blog/
├── index.html              # 唯一入口，所有页面都在这里渲染
├── site.json               # 站点名称、简介、导航、社交链接
├── package.json            # 只是给命令起别名，没有依赖
├── posts/                  # 文章（Markdown）
├── pages/about.md          # 「关于」页面
├── assets/
│   ├── css/style.css       # 全部样式，深浅色双主题
│   └── js/
│       ├── markdown.js     # Markdown 渲染器 + 代码高亮（自己写的）
│       ├── app.js          # 路由、搜索、标签、目录
│       └── posts-data.js   # 构建产物：文章数据
└── tools/
    ├── build.mjs           # Markdown → posts-data.js
    ├── new-post.mjs        # 新建文章
    └── serve.mjs           # 本地预览服务器
```

## 写博客的两个心态提醒

> 不要等「学明白了」再写。博客记录的是**学习过程**，不是教材。写错了很正常，读者（主要是未来的自己）需要看到的是你怎么想的。

还有一点：**别为了写完而写**。写不出来的时候就承认自己还没搞懂，去把代码再敲一遍——写不出来本身就是最有价值的信息。
